## Decisions

- **Skill sync module:** `src/skill.js` exports `skillSourceDir()`,
  `installedSkillDir(cwd, fallbackDir)` and `syncSkill({ cwd, sourceDir })`.
  `syncSkill` returns `[{ path, action }]` with `path` relative and
  `/`-separated (`.agents/skills/nera`, `.claude/skills/nera`) and `action`
  `created` | `updated` | `unchanged`. The command prints the result.
- **Source of the skill on update:** the site's installed
  `node_modules/@nera-static/nera/skills/nera`, used when it has a
  `SKILL.md`. It is read after `npm update`. Otherwise the running package's
  `skills/nera` is used, so an installed nera ≤ 1.9.0 (no skill) falls back.
- **Mirror semantics:** files are compared byte for byte and written only on
  change. Files and folders inside `…/skills/nera/` that the source lacks are
  deleted. A file where the source has a folder is replaced, and so is the
  reverse. A symlink inside `nera/` is removed and never written through.
  Nothing outside the two `nera/` folders is read or written. A source
  without `SKILL.md` throws a "packaging bug" error before anything is
  written.
- **"created" vs "updated":** `created` means the `nera/` folder did not
  exist. `updated` means it existed and anything was written or removed.
- **Order and messages:** on `nera update`, the skill is synced right after
  `AGENTS.md`/`CLAUDE.md`. It prints `✓ Added the Nera skill in <dir>`,
  `✓ Refreshed the Nera skill in <dir>` or `✓ <dir> unchanged`, one line per
  folder. `nera new` prints one line naming both folders.
- **`nera new .`:** dot-folders were already allowed in the target folder,
  so an existing `.claude/settings.json` or `.agents/` is fine and is kept.
  Only `…/skills/nera/` is written.
- **No third folder:** the two folders of D4 are enough, as decided on
  2026-10-12. Cursor and Copilot read both, so they may list `nera` twice.
- **Skill wording follows today's CLI:** the workflow is `nera new` →
  content → plugins → `nera validate` → `nera build --check` → deploy
  `public/`. The skill does not name `--starter`, `nera publish`, `--yes` or
  MCP. `--no-install` is mentioned in prose only, apart from `nera new`,
  because the CLI usage text does not list it. The command test would
  otherwise flag it; see Carry-forwards.
- **The link test ignores examples:** code spans and fenced blocks are not
  checked as links. A recipe's Markdown example such as
  `![alt](/images/x.jpg)` is site content, not a skill link.
- **Frontmatter parsing:** the test parses the frontmatter with `yaml`, a
  dependency of `@nera-static/core` that npm hoists. No new dependency was
  added.
- **Size limits in tests:** `SKILL.md` must stay under 200 lines and each
  recipe at most 80 lines. These are soft guards below the 500-line limit
  in the spec.

## Carry-forwards

- `bin/nera.js:15` (usage text): `--no-install` for `nera new` works
  (`src/commands/new.js:17`) but is not on the usage line. The skill and
  `AGENTS.md` therefore cannot write `nera new <name> --no-install` without
  failing the command test. Not fixed because it is out of scope (CLI usage
  and README change).
- `nera-plugin-search` template (`search.pug`): it ships its own `h1` and an
  unlabelled `<input type="search">`, so `nera build --check` warns
  `a11y-h1`/`a11y-form-label` on every site that uses it as published. This
  belongs to the plugin repo; the recipe works around it.
- Local verification: `npm install <checkout>` symlinks the package, and core
  then resolves plugins from the checkout's `node_modules`, so plugins
  installed in the site fail to load. The boot command in
  `.claude/issue-conventions.md` works only for plugin-free sites; with
  plugins, `npm install --install-links <checkout>` works. A note for that
  file, not changed here.
